# 같은 쿼리, 같은 값인데 2.9초와 8분 — PostgreSQL 제네릭 플랜

최근에 라디오 앱 개발에 참여하면서 청취 통계 서비스 개발을 담당했다. 청취 통계 서비스에는 2분마다 도는 재집계 배치가 있다. 장시간 청취나 오프라인 재전송처럼 늦게 확정되는 청취가 생겼을 때, 이미 집계한 시간대를 다시 계산해 덮어쓴다.

평소 한 회차는 7초에서 26초면 끝났다. 그런데 하루 두 번, 같은 배치가 8분 31초와 6분 18초를 썼다. "마지막 성공 6분 전" 정체 알림이 떴다가 저절로 풀렸다.

입력이 특별했던 것도 아니다. 같은 날짜, 같은 범위를 90초 뒤에 다시 돌리면 8초에 끝났다. 느려진 회차의 SQL을 그대로 DB 클라이언트에 붙여 돌려도 3초면 나왔다. 같은 쿼리를 같은 값으로 실행했는데 2.9초와 수 분으로 갈린 것이다.

원인은 데이터가 아니라 그 커넥션이 들고 있던 실행 계획이었다. PostgreSQL이 6번째 실행부터 파라미터 값을 보지 않는 계획으로 갈아타고, 그 계획이 배열 파라미터의 행 수를 38배 적게 추정했다.

> 환경: PostgreSQL 16, Spring Boot, JdbcTemplate, pgjdbc, HikariCP

## 1. 2분마다 도는 배치가 가끔 8분 걸렸다

한 회차는 여러 단계를 차례로 돈다. 시간별 집계부터 기간 집계까지 순서가 고정되어 있고, 각 단계는 분석용 PostgreSQL에서 읽어 결과를 다시 쓴다.

```text
재집계 배치 (2분 주기마다 잡 감지 후, 잡 존재 시 실행)

  시간별 → 동시 청취자 → 일별 → 프로그램 완청률 → 프로그램 청취 곡선 → 기간
                                                        ^
                                              평소 수 초, 정체 회차에 약 3분

  평소 회차   7 ~ 26초
  정체 회차   8분 31초, 6분 18초
```

청취 곡선은 5분 단위라 방송 하나를 5분씩 끊은 칸(버킷)을 만들고, 버킷마다 그 5분 동안의 청취 초를 채운다. 2시간 방송이면 버킷이 24개다.

```text
u001 의 청취   09:03 ━━━━━━━━━━━━━━━ 09:12

  09:00  │  09:05  │  09:10
 ────────┼─────────┼────────
  120초  │  300초  │  120초     ← 겹치는 만큼 나눠 담는다
```

버킷을 채우려면 그 5분과 겹치는 청취 기록을 찾아야 한다. 그 기록이 쌓이는 재생 구간 표는 월 파티션이고 이번 달 분량이 74만 행이다. 한 회차가 74만 행을 다 읽는다는 뜻이 아니라, 버킷 하나를 채울 때마다 그 크기의 표를 뒤진다는 뜻이다.

앱은 두 대가 각자 커넥션 풀을 갖고, 통계를 쓰는 배치들은 분산 락 하나를 나눠 쓴다. 이 구조가 뒤에서 중요해진다. 같은 코드가 어느 커넥션을 빌렸는지에 따라 다르게 돌기 때문이다.

## 2. 가설 다섯 개 중 네 개를 기각했다

"가끔 느리다"는 증상은 재현이 어렵다. 그래서 가설을 세울 때마다 "다음에 무엇을 보면 이 가설이 깨지나"를 먼저 정하고, 그것만 조회했다.

| # | 가설 | 본 것 | 결과 |
| --- | --- | --- | --- |
| 1 | 같은 분산 락을 쓰는 다른 배치가 락을 오래 쥔다 | 배치 실행 이력 표(시작, 종료 시각) | 기각. 그 배치는 0.5초. 느린 건 재집계 자신 |
| 2 | 어제 날짜 작업이 지난주 전체 재계산을 부른다 | 재집계 작업 표(대상 날짜) | 기각. 6분 회차의 대상은 오늘 06시 1건. 같은 작업이 다른 때는 8초 |
| 3 | 파티션 생성 DDL이 표에 강한 락을 건다 | 같은 시각에 돈 모든 배치의 이력 | 기각. 파티션 배치 0.06초 |
| 4 | autovacuum이 디스크를 차지했다 | `pg_stat_user_tables` 마지막 vacuum 시각, OS 지표 | 기각. iowait 0, Disk I/O 변화 없음 |
| 5 | 쿼리 하나가 CPU만 쓰며 오래 돈다 | OS 지표(CPU, Load), DB 활성 세션 타임라인 | **확인. 곡선 쿼리 1회가 약 3분** |

4번은 아슬아슬했다. 첫 정체가 vacuum 종료 0.08초 뒤에 끝났기 때문이다. 우연으로 보기 어려운 시각 차였지만 iowait가 0이고 Disk I/O에 변화가 없었다. 디스크를 기다린 흔적이 없으면 vacuum은 범인이 아니다.

결정적이었던 자료는 세 가지다.

- **OS 지표의 모양.** CPU가 13 ~ 15%에서 평평했다. 8코어 중 1코어를 꽉 채운 모양이고, Load Average는 1, iowait는 0이었다. 디스크를 기다린 게 아니라 쿼리 하나가 계산만 했다는 뜻이다.
- **활성 세션 타임라인의 `query_start`.** 1초 간격 표본에 같은 PID와 같은 시작 시각이 몇 분간 이어졌다. 짧은 실행이 여러 번 반복된 게 아니라 한 번 실행이 3분이었다.
- **같은 데이터, 다른 커넥션.** 같은 이틀치를 90초 간격으로 계산했는데 한 커넥션은 8초, 다른 커넥션은 6분이었다. 그 느린 커넥션도 4분 전에는 정상이었다.

데이터가 같은데 결과가 갈리면 변수는 입력 밖에 있다. 커넥션 상태가 변수라는 신호였고, 여기서 플랜 캐시를 의심했다.

## 3. 커스텀 플랜과 제네릭 플랜

SQL은 무엇을 원하는지만 말한다. 어떻게 읽을지는 옵티마이저가 정하고, 그 결과가 실행 계획이다. 내비게이션이 경로를 고르는 것과 비슷하다.

1. **후보를 만든다.** 표를 어떤 순서로 합칠지, 인덱스를 탈지 통째로 읽을지, 조인을 Nested Loop, Hash Join, Merge Join 중 무엇으로 할지.
2. **행 수를 추정한다.** ANALYZE가 모은 분포와 조건의 값으로 "이 단계에서 몇 행이 나올까"를 계산한다.
3. **비용을 매긴다.** 행 수에 페이지 읽기와 CPU 비용을 곱해 더한 상대 점수다. 단위는 시간이 아니다.
4. **가장 싼 후보를 고른다.**

핵심은 2번이다. 행 수 추정이 틀리면 비용 비교가 틀리고, 엉뚱한 계획이 "가장 싸다"고 선택된다. 특히 Nested Loop는 바깥 행이 적을 때 싸고, 많을 때 안쪽을 그 횟수만큼 반복해 폭발한다.

### 6번째 실행부터 값을 보지 않았다

준비된 문장(prepared statement)은 파라미터 자리를 빈칸으로 두고 한 번 등록해, 값만 바꿔 여러 번 실행하는 문장이다.

```sql
PREPARE q(int) AS SELECT * FROM orders WHERE customer_id = $1;
EXECUTE q(42);   -- 값만 바꿔 반복 실행
```

이때 PostgreSQL은 계획을 두 가지 방식으로 세울 수 있다.

| | 커스텀 플랜 | 제네릭 플랜 |
| --- | --- | --- |
| 언제 세우나 | 실행할 때마다 새로 | 한 번 세워 세션에 저장 |
| 파라미터 값 | 본다. 값을 상수처럼 넣고 추정 | 보지 않는다. 기본 선택도와 기본 행 수로 추정 |
| 장점 | 값에 맞는 정확한 계획 | 계획 수립 시간이 0 |
| 위험 | 매번 계획 비용(보통 수 ms) | 값에 따라 아주 나쁜 계획 |

기본값인 `plan_cache_mode = auto`의 규칙은 이렇다. PostgreSQL 12 이상, 16 기준이다.

```text
준비된 문장이 만들어진다        ← 이게 먼저. 빈칸($1)을 가진 문장으로 등록
      │
 실행 1 ~ 5   커스텀 플랜으로 돈다
              매번 값을 보고 계획을 세우고, 그 예상 비용을 평균으로 쌓아 둔다
      │
 실행 6       여기서 제네릭 플랜을 처음 세운다 (값을 보지 않고)
              그 예상 비용을 1~5회 커스텀 평균과 비교한다
              제네릭이 비싸지 않으면 → 이후 계속 제네릭
      │
 실행 7 이후  세워 둔 제네릭 플랜을 그대로 재사용. 계획 수립 없음
```

판단은 세션마다 따로 한다. 평균과 횟수도 세션마다 따로 쌓인다.

함정은 6번째의 비교가 **둘 다 추정치**라는 점이다. 제네릭의 행 수 추정이 실제보다 크게 작으면 제네릭이 가짜로 싸 보이고, 그래서 선택되고, 실제 실행은 훨씬 느려진다. 게다가 한 번 갈아타면 실제 실행 시간을 보고 되돌아가는 장치가 없다.

### 코드에 PREPARE가 없는데도 준비된 문장이 생긴다

앱 코드에는 `PREPARE`가 없었다. 그런데도 제네릭 플랜이 생긴 건 드라이버가 알아서 준비된 문장을 만들기 때문이다.

```text
애플리케이션 코드            PREPARE 없음, 바인딩 파라미터만 있다
        |
NamedParameterJdbcTemplate   :name 을 ? 로 바꿔 PreparedStatement 로 보낸다
        |
pgjdbc                       한 커넥션에서 같은 SQL 을 prepareThreshold(기본 5)번
        |                    실행하면, 그다음부터 서버 쪽 준비된 문장으로 바꾼다
        |
PostgreSQL                   plan_cache_mode = auto 규칙이 적용된다
        |
HikariCP                     커넥션을 수십 분씩 재사용한다. 그동안 횟수가 쌓이고
                             커넥션이 교체되면 처음부터 다시 센다
```

결과적으로 같은 코드가 어느 커넥션을 빌렸느냐에 따라 커스텀으로도, 제네릭으로도 돈다.

이 구조 때문에 평소 개발 환경에서는 잘 드러나지 않는다. 로컬과 테스트에서는 커넥션이 짧게 살고 실행 횟수도 적다. psql이나 DBeaver에서 같은 쿼리를 손으로 돌리면 그 세션에서는 항상 커스텀이라 빠르게 나온다. "내 자리에서는 빠른데"가 되는 이유다.

## 4. 제네릭 플랜은 방송 380건을 10건으로 봤다

쿼리는 하루치 편성을 배열 8개로 넘긴다. 배열의 한 원소는 방송 1회가 아니라 편성 블록의 조각 하나이고, 이날은 원소가 380개였다. `IN` 목록처럼 펼치면 원소 수마다 SQL이 달라지므로, 배열을 파라미터로 받아 SQL 안에서 표로 되돌린다.

```sql
WITH airing AS (
    SELECT *
      FROM unnest(CAST($1 AS text[]),                        -- 프로그램 ID
                  CAST($2 AS text[]),                        -- 채널 ID
                  CAST(CAST($3 AS text[]) AS timestamptz[]), -- 방송 시작
                  ...)
             AS p(program_id, channel_id, start_at, ...)
)
-- 방송마다 5분 버킷을 만들고, 버킷과 겹치는 재생 구간의 청취 초를 배분한다
```

이 방식 자체는 나쁜 선택이 아니다. SQL 문장이 하나로 고정되고, 커스텀 플랜에서는 배열 값을 보고 행 수를 정확히 추정한다. 문제는 문장이 고정되니 같은 커넥션에서 금방 6번을 넘긴다는 점, 그리고 제네릭에서는 볼 값이 없어 기본 추정치로 떨어진다는 점이다.

```text
제네릭 플랜이 세운 계산

  unnest($1) 10행  →  5분 버킷 2개      →  인덱스 조회 2번
                                            "싸다", 예상 비용 25,826

실제로 들어온 값

  unnest($1) 380행 →  5분 버킷 3,155개  →  인덱스 조회 수천 번
                                            재생 구간 표(월 74만 행)를 뒤진다
```

| | 커스텀 | 제네릭 |
| --- | --- | --- |
| unnest 행 수 추정 | 335 | 10 |
| 버킷 추정 | 수천 개 | 2 |
| 전체 예상 비용 | 138,288 | 25,826 |
| 고른 조인(청취 초 배분) | Merge, Hash Join | 버킷마다 재생 구간 인덱스를 도는 Nested Loop |
| 실제 실행 | 2.86초 | 수 분 |

버킷 수는 방송 길이에서 나오고, 길이는 배열에 담긴 시작·종료 시각에 들어 있다. 커스텀 플랜은 그 값을 상수처럼 펼쳐 보므로 09:00에 시작해 11:00에 끝나는 방송이 24칸이라는 걸 실제로 계산한다. 제네릭 플랜에서는 그 자리가 `$3`, `$4`라는 빈칸이라 뺄셈 자체가 되지 않는다. 값을 모르는 자리에 쓰는 기본 추정 규칙으로 떨어지고, 그 결과가 2였다. 2는 결론이 아니라 계산을 포기한 자리에 들어간 기본값이다.

버킷이 2개면 인덱스 조회 2번으로 끝나니 Nested Loop가 싸 보인다. 여기서 인덱스는 버킷 쪽이 아니라 재생 구간 표 쪽에 있다. 버킷은 저장된 표가 아니라 쿼리를 도는 동안 배열에서 만들어지는 중간 결과라 인덱스도 통계도 없다. 버킷 하나가 채널과 시간 범위를 검색어로 주고, 그 조건으로 재생 구간 표의 인덱스를 찾는 구조다.

```text
for 버킷 in 3,155개:            ← 바깥
    재생 구간 인덱스 조회(버킷)  ← 안쪽, 버킷 수만큼 반복
```

제네릭은 이 반복이 2번이라고 믿었다. 그래서 예상 비용이 커스텀의 5분의 1로 나오고, auto 규칙이 제네릭을 고른다. 실제로는 3,155번이었고, 74만 행 표의 인덱스를 수천 번 뒤지며 CPU만 쓴다.

버킷의 크기를 알 방법이 파라미터 값을 보는 것밖에 없다는 점이 이 사건의 뿌리다. 저장된 표라면 ANALYZE가 모아 둔 통계로 대략의 행 수를 알 수 있지만, 배열에서 그때그때 만들어지는 중간 결과에는 그 통계가 없다. 값을 보지 않는다는 제네릭 플랜의 성질과 정확히 맞부딪혔다.

이 계획은 데이터가 적을 때는 금방 끝났다. 재생 구간이 쌓일수록 반복 한 번의 비용이 커져 수 분이 됐다. 나쁜 계획은 이용자가 늘수록 더 느려진다. 오늘 괜찮았다는 사실이 내일을 보장하지 않는 쪽이다.

> 덧붙이면, 집합 반환 함수의 행 수를 플래너가 모를 때의 기본값은 보통 크다(1,000). `unnest`는 배열 상수면 원소 수로 추정한다. 이번 제네릭 계획에서는 `rows=10`으로 찍혔다. 숫자는 버전과 쿼리 형태에 따라 다를 수 있으니 자기 환경에서 `EXPLAIN`으로 확인하는 게 맞다.

## 5. 두 계획을 나란히 태워 증명했다

지나간 커넥션이 어떤 계획을 들고 있었는지는 남지 않는다. 대신 같은 문장을 같은 값으로 두 계획에 강제로 태워 비교하면 증명이 된다. DB 클라이언트 하나, 세션 하나로 된다.

```sql
-- 0. 앱과 같은 조건 (이 세션에만)
SET jit = off;                            -- 앱이 이 쿼리에서 JIT 을 끄므로
SET max_parallel_workers_per_gather = 0;  -- 원문이 INSERT 라 병렬을 못 쓴다
SET statement_timeout = '5min';

-- 1. 앱의 SQL 을 빈칸 그대로 등록 (INSERT 는 SELECT 로 바꿔 쓰기 없이)
PREPARE q(text[], text[], ..., timestamptz) AS WITH airing AS (...) SELECT ...;

-- 2. 계획만 비교 (실행하지 않는다)
SET plan_cache_mode = force_custom_plan;  EXPLAIN EXECUTE q(<실제 값>);
SET plan_cache_mode = force_generic_plan; EXPLAIN EXECUTE q(<실제 값>);

-- 3. 실제 시간 (읽기 전용 트랜잭션)
BEGIN READ ONLY;
SET LOCAL plan_cache_mode = force_generic_plan;
EXPLAIN (ANALYZE, BUFFERS) EXECUTE q(<실제 값>);
ROLLBACK;
```

실제 하루치 편성 값으로 돌린 결과다.

| 계획 | unnest 행 추정 | 예상 비용 | 실행 시간 |
| --- | --- | --- | --- |
| 커스텀 | 335 | 138,288 | 2.86초 (계획 수립 2.8ms) |
| 제네릭 | 10 | 25,826 | 수 분 (취소) |

같은 값인데 추정이 335와 10으로 갈렸고, 그 차이가 조인 방식을 바꿨다. 가설은 여기서 확인됐다.

돌리면서 걸린 것도 몇 가지 있다.

- **값을 넣는 법.** 배열 8개를 손으로 만들 수 없어, 원본 표에서 `format('%L, %L, ...', array_agg(...), ...)`로 인자 문자열 하나를 만들어 붙여 넣었다.
- **DB 클라이언트의 파라미터 처리.** DBeaver는 `$1`을 자기 변수로 알고 입력창을 띄운다. 무시하거나 설정에서 끈다.
- **운영 DB 부담.** `EXPLAIN`은 실행하지 않아 부담이 없다. `EXPLAIN ANALYZE`는 실제로 도니 `statement_timeout`을 걸고, 쓰기 문장은 `SELECT`로 바꿔 `BEGIN READ ONLY` 안에서 돌린다.
- **SELECT 로 바꾼 차이.** 결과에 쓰이지 않는 CTE 는 플래너가 생략할 수 있다(never executed). 느려지는 부분이 결과에 남아 있는지 확인해야 비교가 성립한다.

## 6. 트랜잭션 안에서만 커스텀 플랜을 강제했다

문제 쿼리의 트랜잭션 안에서만 커스텀 플랜을 강제하기로 했다. 영향 범위가 가장 좁고, 되돌리기도 한 줄이다.

```java
@Transactional(transactionManager = ANALYTICS_TX)
int replaceDay(...) {
    jdbc.update(DELETE_DAY, day);
    jdbc.execute("SET LOCAL jit = off");
    jdbc.execute("SET LOCAL plan_cache_mode = force_custom_plan");  // 추가
    return jdbc.update(INSERT_DAY, params);
}
```

계획 수립 3ms 를 매 실행마다 내는 대가로 값에 맞는 계획을 보장받는 거래다. 2분 주기 배치에서 3ms 는 문제가 되지 않는다.

같은 배열 파라미터 패턴을 쓰는 다른 쿼리(완청률 등)에도 같은 설정을 걸었다. 배포 후에는 배치가 남기는 단계별 소요 시간으로 곡선 단계가 다시 수 분으로 늘지 않는지 본다.

## 7. 마무리

증상은 "가끔 느린 배치"였고, 원인은 데이터가 아니라 커넥션이 들고 있던 실행 계획이었다. pgjdbc 가 같은 SQL 의 반복을 보고 서버 준비된 문장으로 바꾸고, PostgreSQL 이 그 문장의 6번째 실행에서 제네릭 플랜으로 갈아타고, 그 계획이 배열 파라미터를 10건으로 추정했다. 세 단계 모두 각자의 자리에서는 합리적인 최적화다.

"가끔만 느리다"는 증상은 데이터보다 실행 환경의 상태(커넥션, 캐시, 통계)를 먼저 의심할 만하다. 같은 입력이 빠르기도 느리기도 하다면, 그 차이를 만드는 것은 입력 밖에 있다.

아래 신호가 겹치면 플랜 캐시를 의심해 볼 만하다.

- 같은 쿼리를 같은 값으로 실행했는데 어떤 때는 빠르고 어떤 때는 수십 배 느리다
- psql 이나 DB 클라이언트에서 직접 돌리면 항상 빠르다
- 느릴 때 iowait 는 없고 CPU 코어 하나만 꽉 찬다
- 배열, JSON, 함수 반환값처럼 플래너가 행 수를 값에서만 알 수 있는 파라미터를 쓴다
- 범위 조건(`BETWEEN $1 AND $2`)의 폭이 호출마다 크게 다르다

추적을 위해 미리 해 둘 일도 있다. 이번 추적의 절반은 배치 실행 이력을 SQL 로 대조한 것이었다. 로그가 아니라 조회 가능한 표로 남겨 두면 "어느 회차가, 어느 단계에서 느렸나"를 DB 쪽에서 역추적하지 않아도 된다. 도구는 정상 회차로 먼저 보정하는 게 좋다. 타임라인이 25초짜리 정상 회차를 정확히 그리는지 확인한 뒤에 정체 구간을 읽었다. 표본 그래프의 0 은 "끝났다"가 아닐 수 있으니 `query_start` 로 같은 실행인지 확인한다.

설계할 때 기억할 것은 두 가지다. 문장을 고정하려고 값을 배열 파라미터로 묶었다면 제네릭 플랜 위험을 같이 따져 본다. 그리고 성능 측정을 한 번 실행으로 끝내지 않는다. 같은 커넥션에서 6번 이상 돌려 봐야 이 문제가 보인다.
